# Changelog

Behavior, not commits. Dates are the day the change landed on `main`.

## 0.1.0 — unreleased

First public version. Nothing is tagged yet, so this entry describes the skill as it stands at launch rather than a diff from anything.

- Two modes. Audit reports whether a repository's claims match its code. Launch audits first, proposes a plan, and writes only what was approved.
- The enforcement gate: every claim that something is prevented, blocked, refused, required, or guaranteed is classified Enforced, Advisory, Guidance, or Unsupported against the mechanism behind it. Scope and liveness count — a guard over one directory does not back a claim about the build, and a workflow step that no longer runs never fails.
- Six opt-in checklist packs, with Safety gates mandatory before a public flip. A checklist the audited repo ships outranks all of them.
- Six swap-in modules under `checklists/modules/`, selected by the repo's shape rather than the user's intent. Each states the trigger that makes it apply and is offered, not applied: self-proof (the product is a judgment and the repo is made of what it judges), MCP server (the repo ships one), single source of truth (a number is written in more than one file), pinned knowledge (the repo restates a third-party spec), live data (a published number comes from a scheduled job), and evidence grading (the repo itself ships a grader). With no interactive caller, modules whose triggers are objectively met are applied anyway, listed with the observed trigger, and their findings tagged with the module that produced them.
- The MCP server module. Its first item is the install trap: a README config block running `npx -y <pkg>` against a name that is not on npm, checked with `npm view`, alongside the npm version badge that renders broken for the same reason. An unpublished repo leads with the local `node /absolute/path/dist/index.js` form instead. Then `server.json` `name` against `package.json` `mcpName` (registry ownership validation reads it), version agreement across `server.json`, `packages[]`, and `package.json`, schema validation including the `packageArguments` type discriminator, whether the publish workflow can do the *first* publish at all given that npm Trusted Publishing cannot be configured for a package that does not exist yet, and bounded tool results.
- Self-proof needs two triggers now, not one. The product must be a judgment **and** the repo's own primary artifact must be of the type the tool judges. A social-post checker's repo contains no social posts, so "runs on itself in one command" is unsatisfiable rather than unmet, and running the module straight filed three `P1`s a maintainer could not fix. When only the first condition holds, the spirit still applies (publish the unflattering number, name what was not measured) and the mechanical checks do not.
- Uncommitted working-tree changes are reported separately and never reduce the counts: they are invisible to a clone, absent from a public flip, and gone on the next checkout. Step 0 also re-checks `git status` and `HEAD` at the **end** of the audit, and pins the report to the SHA that was actually read when the tree is dirty or has moved. The stale-checkout guard covered a tree that was old; this covers one that moves while it is being read.
- A **Conditional** verdict in the enforcement table, for a defect that is real code on a reachable path whose trigger depends on external behavior that could not be observed. The convention: file it, state the condition and what would settle it in the body, keep the severity at the impact if the condition holds rather than hedging it down, put the settling command under `Required verification`, and list the adjacent paths checked that were not defects.
- A `Verified clean` section in the report, between the header block and `P1`. `Evidence checked` says what was inspected and the severity sections say what is wrong; neither could say a specific thing was checked and passed, so a caller who asked about one thing read the silence as "not examined." It holds requested checks and checks a reader would assume were skipped, not everything that passed.
- The safety-gate leak pattern is derived, not remembered. `gh repo list <owner> --visibility private --json name` yields the exact alternation of private repository names, which is the half of the pattern nobody thinks to type; org, employer, and client names are still added by hand.
- The demo artifact takes the product-shape exception. For `library` and `service` shapes with no TTY surface, such as an MCP server speaking JSON-RPC over stdio, a worked request and response satisfies the item, because a recording of the wire format shows a JSON blob scrolling past. The artifact still has to show the value, and a GIF of a human-readable wrapper is better than the code block where one is achievable.
- The contribution-path check asks for the content **and** the location: a contribution path that exists only in the README is content in the wrong file, so the finding is "move it, keep it," not "no contribution path exists."
- The evidence bar is in the skill itself, not a pack. A verdict needs a `file:line` or an explicit searched-and-found-nothing note; a grep miss alone does not establish Unsupported, because the target names things its own way and a false Unsupported is a false accusation; an open PR is verified against its diff, not its title, and what it fixes moves to `Known / in-flight`; every finding names the file, guard, or test to change.
- License fit is checked, not just license presence. Apache-2.0 for code others depend on (the patent grant is the reason, not the credit), MIT for small single-purpose repos, CC-BY-4.0 for curated lists and datasets because a software license makes a claim data cannot support, and matching the upstream for a derivative. The pack also records that MIT already compels credit, so wanting attribution is not a reason to switch, and that relicensing is forward-only.
- Safety gates now scan metadata as well as the tree. Commit messages, branch names, tags, and PR and issue text are checked against the same pattern as the file scan, because a leak in a commit message survives fixing the file and needs a history rewrite that forks and `refs/pull/*` never see.
- Five README templates chosen by product shape, each with a `What's enforced` table so a generated README states its mechanisms rather than earning a P1 on the next audit.
- Reports carry `Evidence checked` and `Coverage limits`. Coverage limits cannot be omitted; an empty one is a claim that everything was checked.
- Install pulls the whole skill directory. `SKILL.md` on its own now fetches a missing checklist or template from `raw.githubusercontent.com`, and reports what it could not fetch instead of proceeding without it.
- `NOTICE` records the structure adapted from Nnenna Ndukwe's Apache-2.0 work.
