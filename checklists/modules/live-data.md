# Live data

**Trigger:** any workflow under `.github/workflows/` carries a `schedule:` key, or a number rendered on a page comes from a JSON file, a data endpoint, or a committed snapshot rather than from prose someone typed.

The question this module asks: **does the repo distinguish "the fetch succeeded" from "the data is recent"?** Those are different facts, and conflating them is how a page keeps advertising numbers as live for days after the job producing them died.

The checks below were generalized from a site build where exactly that happened. An `isLive` flag meant only "the HTTP call worked," so when the upstream refresh cron stopped, every page went on claiming it updated live over numbers that were nine days old — and nothing on the page could have told a reader. The fix is the module; the incident is why each item is in it.

- [ ] **The producer stamps every payload with the time it was generated.** Not the time it was fetched — the time the numbers were computed. A `generated_at` field is what gives a consumer an age at all; without one there is no honest option but to trust the transport. `P1`.
- [ ] **The consumer compares that stamp against a stated max age, and a stale-but-successful fetch degrades to the same presentation as a failed one.** Size the window to tolerate one missed run without crying wolf — 48 hours against a daily producer — and put the reasoning next to the constant. Stale data can still be served, since it is the freshest thing available; it just stops being labelled live, and any animated or projected display is suppressed, because a stale anchor is what those projections cannot survive. `P1`.
- [ ] **A "live" claim names the mechanism that retracts it, or the word does not appear.** Declaring the number a committed snapshot and rendering its date is equally valid — a stale number then reads as stale. What fails is the word with nothing behind it. `P1`.
- [ ] **The freshness signal is visible to a human reading the page, not only to a log.** A `console.warn` on stale data goes to a build log nobody opens. The load-bearing part is what the page does: swap the live indicator for an `As of <date>` label carrying **the data's own** timestamp rather than a hand-synced constant, which would understate how current the served numbers actually are. A monitor only the maintainer could find is not a retraction. `P1`.
- [ ] **The producer pushes; the consumer does not cron on a guessed offset.** A consumer job fired at an offset guessed from the producer's run time is wasteful when nothing moved and actively wrong when the producer fails, because it re-bakes stale numbers into a fresh deploy — cheerfully, every morning, for as long as nobody looks. Have the producer trigger the consumer as its last step so a rebuild happens when and only when there is new data, and keep `workflow_dispatch` so one can still be forced by hand. `P2`.
- [ ] **Every scheduled job sets `timeout-minutes` from an observed maximum, with that observed figure in a comment beside it.** An uncapped job inherits GitHub's 360-minute default; one hung run at that length can eat a fifth of a monthly free-tier budget, and an exhausted budget is itself a way for a producer to die silently. A cap of 5 or 10 minutes against a longest-real-run under a minute is the shape. `P2`.
- [ ] **Concurrent runs cannot race.** Set `concurrency` with `cancel-in-progress: true`. A job that commits a data file loses one of two overlapping pushes; a job that fires a deploy hook merely queues a duplicate build. `P3`.

## README section this contributes

```markdown
## Where these numbers come from

<page or badge> renders <field> from <source>, generated by <producer job>.
The page shows "As of <date>" from the data's own timestamp. If that data goes
older than <max age>, the page drops the live label and shows the date instead
of implying the number is current.
```

Fill it from the code. If the repo cannot say what happens when the producer stops, that is the finding, not a section to soften.
